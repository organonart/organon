### organon.art leads with the role, and stops repeating a §12 that has gone stale

The page opened on `doc/organon_prd.md` §1.1 — *"Organon is a native GPU application. You divide
the window into regions…"* — on the rule that §1.1 is canonical and every surface quotes it. The
rule is right and the placement was wrong: §1.1 is a **definition**, and leading with a definition
made the front page read as a specification rather than an idea. James's framing is the one the
page now carries: this is the harness you sit in all day, it opens on a blinking cursor, and the
thing no terminal harness can do is grow.

So the headline is **"An extensible ecosystem that starts as a blinking cursor."**, the standfirst
says what it replaces, and §1.1 appears **verbatim and unchanged** one screen down, under *The
definition, in the words the repository uses*. 📌 **Quoting §1.1 is an obligation about wording,
not about position** — that distinction is now written into `site/README.md` so the next person
does not restore the definition to the top believing the rule requires it.

A new §The role carries the positioning, and it names the two doors: **skills** teach the agent
and **modules** teach the window, neither requiring Organon to be rebuilt.

🚨 **Writing it found that the PRD's §12 has gone stale in the one place the site was repeating
it.** §12 is dated 21 August and says *"the hosted-module protocol and the verb that runs one do
not exist"*. Four tiers landed after it — T3a's manifest and grants, T3b's clone/diff/build, T4's
producer qualifier and T5's launcher — so today a module is cloned, diffed against the commit you
last approved, built, launched, and painted into a named region, and `organonart/ascent` is a real
one. The site's *State of play* now describes that, and carries an explicit note that it is ahead
of §12 rather than quietly disagreeing with it. ⚠️ **The PRD itself is not touched here** — it is
owned outside this change and a website should not be the thing that edits a product definition —
but §12 needs the same correction, and this fragment is the notice.

⚠️ **What survives from that §12 paragraph is the narrower and better half**, and the page says it
where it matters rather than as a caveat: *no `dlopen`, no wasm*. **A module is a process, not a
plugin.** That is a design decision, not an unbuilt feature — approval gates *building*, because a
build script runs as you before any of the module's own code does, and the process boundary gates
*running*. Describing modules as plugins loaded into the application would have been both wrong
and a worse story.

✏️ **One consequence of T4 is now stated where it reads as a payoff rather than a detail.** The
one-live-viewport limit was always attributed to *that renderer* — its shared frame index and
jitter phase — rather than generalised into the region model, and §What an arrangement holds said
so. That attribution has since been cashed: because the limit belongs to the producer,
**two hosted viewports are legal**, and a second producer changed one function and the site that
renders it without touching the region model, the layout or the vocabulary.

### organon.art is painted in the application's own palette

The page had been white, then warm bone, and both read as white. The first attempt at dark derived
a ground by taking pi.dev's `#161d27` — HSV(215°, 44%, 15%) — and rotating **the hue alone** to
Organon's mark hue of 41°, giving `#272216`. It was a defensible derivation and it was answering
the wrong question: **Organon already has a palette, and it is in the tree.**

🚨 **Every colour on the page is now copied from `native/src/theme_config.rs`'s shipped blue-slate
`Palette::default()`**, and the CSS custom properties carry that file's own surface names —
`shell` `#192228` as the ground, `panel` `#212a30`, `raised` `#273139`, `well` `#141c22` for
recessed things, `hairline` `#3a464f`, `edge_strong` `#52616b`, `bone` `#d1d6d9` for type,
`titanium` and `muted` beneath it. The plates are `well_deep` and `well` framed in `card_header`,
which is what makes them read as inset wells rather than cards. A page that is a picture of
Organon should be painted in Organon's colours, not in colours chosen to resemble them.

⚠️ **It is a copy, and the consequence is accepted rather than hidden**: if the theme moves, this
is wrong. The trade is that it drifts *detectably* — every value is named after the token it came
from, so a diff against `Palette::default()` is mechanical — where a palette that merely rhymed
with the product would drift silently and nobody would ever check.

🚨 **This found a second stale claim, and it is the same class as §12.** PRD §5.4 still specifies a
warm graphite shell, *"near-black with a hint of brown, never blue-black"*. The shipped theme is
blue-slate and `theme.rs` says so in its own comments — *"Under the warm shell this painted every
card title at once, which is why nothing read as emphasis; the blue-slate system is stricter
still"*. So the theme moved and §5.4 did not follow. **The code is what ships, so the page follows
the code**, and §5.4 is what needs correcting. ✏️ The earlier draft of this page had cited §5.4 as
justification for a warm ground — which would have made the website the last surviving witness to
a decision the application had already reversed.

📌 **Chroma is rationed by construction, using the theme's own rule**: *"strong chroma belongs to
data, selection, and status, and every saturated pixel spent on chrome devalues the data."* So the
small mono labels are grey rather than teal, and **teal and amber are deliberately not declared as
page-level tokens at all** — they reach the page only through `--pane-accent` and `--pane-warn`,
which is what keeps the rule structural instead of remembered. Teal appears in exactly one place:
the provenance plate, which is what teal is for in the application. The link colour is `selected`
lightened, because at its shipped `#5d788c` it reaches only 3.7:1 against the shell.

⚠️ **Every colour in the two figures was hardcoded hex** from the light design and would have drawn
pale-grey diagrams on a dark ground — the exact failure the single-theme rule exists to prevent.
They are token-driven now, written as inline `style` rather than as presentation attributes,
because a presentation attribute does not accept `var()`.

⚠️ **This page is now dark and `organonmind.org` is stark white.** That divergence is a decision,
recorded in the token block and in `site/README.md` so it does not get "fixed": the family
resemblance is carried by the *structure* — the tracked-monospace wordmark, the labelled meta
block, the measure, the colophon, the refusal to advertise — and one site is a publication while
the other is the front door to an application whose own shell is dark.

### And `/docs` follows it, because a light docs page beside a dark home is a split site

`site/docs.html` landed from a parallel session written against the light palette, hours before the
palette changed. Its `:root` block was deliberately written to mirror `index.html`'s — which is
what made porting it a token swap rather than a re-typesetting, and is the payoff for that
session's decision to keep the two blocks identical rather than letting the docs page grow its
own.

⚠️ **One thing did not port mechanically.** Its panels were `background:var(--paper)` — correct on
a light ground, where a card is the same white as the page and a border does the work. On a dark
ground that makes every panel vanish into the field, so they are `--panel` now and lift the way
`index.html`'s do. **A token swap is not a palette port**; the surfaces have to be re-read against
the new ground, and this is the one place where "byte-identical token blocks" would have hidden
a defect rather than prevented one.
